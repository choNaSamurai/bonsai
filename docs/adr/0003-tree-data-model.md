# ADR-0003: Плоска таблиця вузлів (SoA-подібна) замість рекурсивного immutable-дерева

- **Статус**: Proposed
- **Дата**: 2026-10-03
- **Автор**: Unity Architect, Gameplay Developer
- **Пов'язані задачі**: PA-102, PA-103, PA-105A, PA-105B

## Контекст
ТЗ (§3.1) описує `@immutable TreeNode` з `children` і `copyWith`. У C#/Unity це дає: алокації на кожну мутацію всього шляху до кореня, рекурсивні обходи в рендері й хіт-тестах, складну серіалізацію. Ліміт — 200 вузлів.

## Рішення
- `TreeGraph` у Domain тримає преалокований `NodeData[200]` (struct), `ParentIndex` замість `children`, стабільний `Id` (int, монотонний), `Version` (++ на мутацію).
- Масив упорядкований **топологічно** (батько завжди перед дитиною) → прохід «зверху вниз» без рекурсії для world-позицій, мешу, FK-перевірки Pot Lip.
- Мутації — лише методами Domain (`Grow`, `Prune`, `ApplyWire`, `SimulateHours`). Зовні — `ReadOnlySpan<NodeData>`.
- **Незмінність** зберігається на межі: `TreeSnapshot` (immutable record) — для збереження, хроніки (<5 КБ/день) і тестів.
- Стан дроту — у самому вузлі (`WiredAtUtcMs`, `WireProgressDays`), окремого реєстру `activeWiredNodeIds` немає → проблема dangling wire ID зникає за побудовою.

## Розглянуті альтернативи
| Варіант | Плюси | Мінуси |
|---|---|---|
| Порт immutable `TreeNode` 1:1 (C# records) | Ближче до ТЗ | GC-тиск, рекурсія, складніший рендер |
| ECS/DOTS Entities | Масштаб | Надмірно для 200 вузлів, великий розмір білда |

## Наслідки
- + 0 алокацій при читанні; рендер перебудовує меш тільки при зміні `Version`.
- + Prune = O(n) компакція, n ≤ 200.
- − Відхилення від буквального тексту ТЗ (Резолюція 3) — фіксуємо тут; доменні інваріанти покриваються EditMode-тестами.
