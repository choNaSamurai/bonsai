# ADR-0004: Процедурний меш гілок уздовж C1-осей + листя подушками з пуфів; анімація у вершинному шейдері

- **Статус**: Proposed
- **Дата**: 2026-10-03 · **Ревізія 2**: 2026-10-05 (PA-102S: арт-напрям L2 Painterly — C1-осі, `AttachT`, мальована кора, Небарі, подушки замість інстансу листків; бюджети)
- **Автор**: Unity Architect, Technical Artist
- **Погоджує**: власник проєкту
- **Пов'язані задачі**: PA-102S, PA-103, PA-104, PA-203, PA-305

## Контекст
Оригінал: single-pass `TreeRenderBox`, 4 `drawPath` (яруси товщини), 1 `drawRawAtlas` для листя, zero-alloc буфери, `rain_sheen.frag`, світлячки як частинки. Ціль — 120 FPS без GC.

Ревізія 2: власник затвердив арт-напрям **L2 Painterly** (`Art/Source/Section_0/realism_l2_painterly.jpg`, `A_Concept/concept_day.jpg`): S-подібний стовбур з різкою конусністю і видимим Небарі, ярусні майже горизонтальні гілки з голими внутрішніми частинами, крона — пласкі **подушки-хмарки** з темнішим низом, кора — мальована текстура з м'яким контуром. Прототип PA-102V показав, що «листок на вузол» + діти на кінчику батька дають «віник». BALANCE §1.2 (Proposed) задає правила форми; тут — як це рендерити.

## Рішення

### 0. Загальна схема
Дерево = **2 draw calls** у steady-state: (1) меш гілок + коріння, (2) меш листя/пуфів/бруньок/квітів. Обидва — `MeshRenderer` з одним `Mesh` (`MarkDynamic`), перебудова **лише при зміні `TreeGraph.Version`** (ріст раз на добу, зріз, дріт) із преалокованих `NativeArray` через `Mesh.SetVertexBufferData`/`SetIndexBufferData` (0 B GC; за потреби — Burst job). Анімація (вітер, дихання Дзен, посуха, сезони, Dormancy) — лише параметри шейдера; CPU не рухає вершини щокадру.

Вхід перебудови: `ReadOnlySpan<NodeData>` → `TreeShapeAnalysis` → `TreeGeometry` (ADR-0003 §4–§5, Domain, double) → float-вершини. Хіт-тест PA-104 і дріт PA-105B читають ту саму `TreeGeometry`.

### 1. Гілки — меш уздовж C1-осей
- **Осі.** Дерево розбивається на осі: ланцюг вузлів через апікальних дітей (`BranchSide = 0`), що починається з #0 або з будь-якої бічної дитини. Стовбурний ланцюг + вісь крони — одна вісь; кожна первинна/вторинна гілка зі своїми продовженнями — окрема вісь. Кожна вісь — **одна безперервна стрічка** без внутрішніх стиків (немає круглих кап між сегментами осі, немає T-junction-артефактів).
- **Крива осі.** Через стики вузлів — центрипетальний Catmull-Rom → кубічні Безьє-сегменти з узгодженими дотичними (C1). `Curvature` вузла додається поверх як зміщення вздовж нормалі до хорди функцією `b(t) = 16t²(1−t)²` (нульове значення **і похідна** на кінцях → C1 зберігається); амплітуда в t = 0.5 = `0.75 · Curvature · CurvatureOffsetRatio · Length` — збігається з серединою кубічного Безьє PA-102V (BALANCE §1.2.6), тож форма гілок не змінюється відносно прототипу, зникають лише злами. Це застосовується до **всіх** осей, не лише до стовбура (BALANCE §1.2.3 вимагає C1 лише для стовбура — див. «Відхилення»).
- **Кріплення.** Основа бічної осі = точка на кривій батька при `AttachT` (де Кастельжо на сегменті батька). Початок стрічки зсувається назад усередину батька на `0.5 · ширина батька` вздовж власної дотичної → «комір» гілки без щілини; бічна вісь малюється **після** батька (порядок осей = порядок кореневих індексів), тож комір лягає поверх кори батька.
- **Профіль ширини** (BALANCE §1.2.2): `w(t) = lerp(Thickness, tipWidth, t)` уздовж вузла; `tipWidth = max(Thickness(ApicalChild), Thickness · TerminalTipRatio)` (без апікальної дитини — `Thickness · TerminalTipRatio`, 0.45). `max` прибирає «шийку», коли на товстому сегменті з'являється тонка брунька (напр. Фенікс 2.5 на стовбурі 10.8): стрічка дитини перші `JointBlend` = 15% довжини плавно звужується від ширини стику до власного профілю. Кінець осі — напівкругла капа.
- **Небарі — частина мешу стовбура** (BALANCE §1.2.4): розширення основи `w(y) = th0·(1 + F·e^{−y/(1.5·th0)})` — додаткові перерізи в нижній частині осі #0; коріння (2–7) — окремі звужені до 0 стрічки в тому ж мешу й тим самим матеріалом кори, кількість/довжина/кут — з `th0`, `TrunkInitialThickness` і хешу `(Seed, rootIndex)`. Поява нового кореня — плавна за `NebariRootFadeSec` через вершинний атрибут «вік кореня» (шейдер масштабує довжину), без перебудови щокадру.
- **Кора, UV.** Дві безшовні мальовані текстури в одному матеріалі: `_BarkTrunk` (B2 v2 `bark_trunk_v2`) і `_BarkYoung` (`bark_young_v2`), 512², wrap Repeat, ASTC.
  - `v` = довжина дуги осі / `BarkTileWorld` — неперервна вздовж осі (одна вісь = одна стрічка, без стрибків на стиках); бічна вісь стартує з `v = hash(Id)` → немає однакового візерунка на сусідніх гілках.
  - `u` = позиція поперек ∈ [0, 1] × `w / BarkTileWorld` → ізотропна щільність текселів на товстих і тонких гілках (немає «розтягнутих» тонких пагонів).
  - Бленд trunk ↔ young — вершинний атрибут `barkAge = smoothstep(YoungMaxWidth, TrunkMinWidth, w)` з поправкою на `Order` (ord 0 тяжіє до trunk), інтерполюється вздовж осі → плавний перехід, без швів.
  - Painterly-деталі в шейдері: фальшиве циліндричне затінення за `u` (світло зліва-згори), м'який темний контур біля країв стрічки (як ink-лінія в `concept_day`), антиаліасинг краю через `fwidth` замість MSAA.
- **Бюджет** (200 вузлів, Д80 без обрізки, адаптивні перерізи: ланцюг 8–10/вузол, гілки 4–6, вторинні 3): ≈ 1 100 перерізів × 2 = 2 200 вершин + ~100 кап кінчиків × 5 + коріння 7 × 12 + розширення основи ~20 → **≈ 3 000 вершин, ≈ 4 500 трикутників**. Преалокація — 8 192 вершини / 12 288 трикутників (worst case 200 × 12 перерізів), індекси `ushort`. Формат вершини ≈ 32 B (pos float3, uv float2, color32, атрибути float3: `barkAge`, `flex`, `windPhase`) → завантаження ≈ 100 КБ на перебудову (раз на добу/зріз).

### 2. Листя — подушки з пуфів
- **Хто несе листя** — лише `IsLeafy` (ADR-0003 §4, BALANCE §1.2.5). Стовбур і внутрішні частини гілок голі.
- **Пуф** = один спрайт подушки з атласу D5 (`sheet_pads_<species>_v1`, 9 форм: 3 малі / 3 середні / 3 великі), а не окремий листок. На leafy-вузол `PuffsPerNode` = 2 пуфи (t = 0.5 і 1.0 на кривій вузла), радіус `PuffRadius × LeafScale`, сплющення `PadFlatten`; розмір форми (S/M/L) — за `PadSize` і `LeafScale`, варіант — хеш `(Seed, Id)`. Перекриття неправильних контурів дає об'єднаний силует подушки; для `PadSize < PadFullNodes` пуфи менші й розставлені окремими пучками.
- **Свіжий приріст**, бруньки (D4), квіти Yamazakura (D3), «свічки» Kuromatsu — квади в **тому ж мешу** й атласі → той самий draw call.
- **Геометрія пуфа**: tight-меш спрайта (8–12 вершин за контуром альфи, Unity Sprite Mesh Type = Tight) замість квада → −30…40% прозорих фрагментів. Пуфи з `LeafScale < 0.02` не додаються.
- **Сортування** (один draw call → порядок = порядок індексів, CPU-сортування при перебудові, преалоковані ключі, без алокацій): подушки — за висотою кореня подушки (нижні яруси раніше, апекс останнім, рівні — за `Id`); у подушці — пуфи знизу вгору, свіжий приріст останнім. Так світлі верхні пуфи перекривають темні низи сусідів, купол апексу лягає поверх. Меш листя — Sorting Layer `Leaves`, вище за гілки (`Tree`) → подушки ховають кінці гілок, як у референсі.
- **Нижня тінь** (`PadUndersideShade = 0.25`): вершинний атрибут `padLocalY` (−1 низ … +1 верх у межах подушки) → шейдер затемнює низ подушки як цілого, а не кожного пуфа окремо. Якщо D5-спрайти вже мають запечений темний низ — TA ставить параметр у 0 (не подвоювати). Без окремого проходу тіні.
- **Сезони й Dormancy — параметри матеріалу**, без перебудови мешу:
  - `_SeasonTex` (осінній/квітковий лист атласу з тією ж розкладкою) + `_SeasonBlend` 0..1; `_FoliageVisible` 0..1 — частка видимих пуфів (Momiji взимку 0; Dormancy 0.20) за хешем `Id` у вершинному атрибуті; невидимі пуфи **схлопуються у вершинному шейдері** (масштаб 0) → нуль фрагментів, без `discard`;
  - `_Desaturation` (Dormancy 0.40), `_FreshTint` (+15% value за атрибутом `freshness`), `_Wetness` (rain sheen), `_Droop` (посуха, −12°).
  - Глобальні значення сезону/доби — `Shader.SetGlobal*` раз на зміну стану (не щокадру); на дерево — власний екземпляр матеріалу, створений один раз (а не `MaterialPropertyBlock`, який вимикає SRP Batcher), `SetFloat` з кешованими ID властивостей лише при зміні значення.
- **Вітер** — у вершинному шейдері, **спільний HLSL-include** для гілок і листя: зміщення = f(`_WindTime`, позиція якоря, `flex`, `windPhase`). Пуф несе позицію і `flex` точки кріплення (вершини гілки в цій точці мають ті самі значення) → подушка рухається разом зі своєю гілкою + власне легке колихання (±0.8°, 3.5 с — ARCHITECTURE §6.2). `windPhase` — хеш `Id` кореня подушки → подушка гойдається як ціле. Дихання Дзен — масштаб Y×1.015 від основи стовбура в обох шейдерах.
- **До появи арту D5** — плейсхолдер-атлас тієї ж розкладки (3×3), згенерований Editor-скриптом із процедурних плям (еліпс + шум контуру + темний низ). Той самий шейдер і шлях даних, без shader keyword → заміна арту = заміна текстури (TD-020).
- **Бюджет**: leafy ≈ 50–70% вузлів → 200–280 пуфів на Д80 (max 400 при `PuffsPerNode` 2) + до ~40 квадів бруньок/свічок. Tight-меш 10 вершин → **≈ 3 000 вершин** (преалокація 6 144). Атлас — на породу 1024² ASTC 8×8 (≈ 0.25 МБ + mips), сезонний варіант — ще один; кора 2 × 512² ASTC 6×6 (≈ 0.1 МБ кожна).

### 3. Draw calls сцени з деревом

| Що | Draw calls | Примітка |
|---|---|---|
| Гілки + коріння + розширення Небарі | 1 | одна текстурна пара кори в одному матеріалі |
| Пуфи + бруньки + квіти + свічки | 1 | атлас породи + сезонний атлас |
| Мох/ґрунт поверх коріння (`SoilFront`) | 1 | належить горщику (PA-203), потрібен, щоб коріння «пірнало» в мох; Sorting Layer між `Tree` і `Leaves` |
| Відрізане піддерево, що падає (0.35 с) | +2 тимчасово | меш з пулу, ARCHITECTURE §6.4 |

Дерево — **2**, з горщиком/фоном/FX — **6–8** на сцену (без UI). SRP Batcher сумісний (один матеріал на меш, властивості через CBUFFER).

### 4. Overdraw і fill rate
Розрахунок на 200 вузлів, Д80 без обрізки, Momiji (найбільші пуфи: r = 9, rx = 11.25, ry = 7.3 units), дерево вписане в ширину портретного екрана (≈ 5 px/unit на 1179 px):
- площа еліпсів пуфів ≈ 260 units² × 240 ≈ 62 тис. units²; площа квадів ≈ 470 units² × 240 ≈ 113 тис.; з tight-мешем ≈ 75 тис.;
- видима площа крони ≈ 13 тис. units² → **глибина перекриття в кроні ≈ 4–5× (піки 6–8 у густих подушках)**;
- відносно екрана (≈ 120 тис. units²): листя ≈ **0.6–0.9 екрана** фрагментів, разом із фоном (1.0), горщиком і гілками ≈ **2.2–2.6× екрана за кадр**.
- iPhone (1179×2556 ≈ 3 MP) @120 FPS ≈ 0.8–0.9 GP/s змішаних фрагментів — у межах для Apple GPU (TBDR, блендинг на чипі). Android mid-tier (2400×1080, Mali-G57/Adreno 6xx) @120 FPS ≈ 0.7 GP/s — на межі; @60 — запас ×2.

Ризики напівпрозорих пуфів і як знімаємо:
1. **Fill rate** на слабких Android → tight-меш; фрагментний шейдер ≤ 2 вибірки (друга — лише при `_SeasonBlend > 0`), `half`; `discard`/alpha-test не використовуємо (ламає HSR на Apple/PowerVR); профіль `LowEnd`: `PuffsPerNode` 1 з більшими формами, render scale 0.8; `OnDemandRendering` у простої (ARCHITECTURE §6.5).
2. **«Шви» при напівпрозорості цілого шару**: якщо згасати листя глобальною альфою (сезон, Dormancy, зріз), перекриття пуфів стають видимими темнішими плямами. Правило: згасання — **масштабом/розчиненням окремого пуфа**, ніколи не загальною альфою шару; без offscreen-RT (зайвий прохід і пам'ять).
3. **Порядок** у межах одного draw call фіксується при перебудові: вітер не міняє порядок, тож мерехтіння сортування немає; між подушками різних ярусів можливі «неправильні» перекриття при сильному дроті — прийнятно для painterly.
4. **Розмір білда**: кожен атлас 1024² ASTC 8×8 ≈ 0.25–0.35 МБ download; 3 породи × (база + сезон) ≈ 1.5–2 МБ — треба врахувати в бюджеті Android ≤ 25 МБ (baseline 18.2) → якщо тісно, 2048²-джерела D5 ріжуться в атлас 1024² або 512² для S/M форм.

### 5. Інше (без змін з редакції 1)
- **Rain sheen** — `_Wetness` у шейдері листя. **Світлячки** — `ParticleSystem`.
- **Знімок для віджета/Polaroid** — окрема камера → RenderTexture → `AsyncGPUReadback`.
- Шейдери — Shader Graph, ціль URP 2D Sprite-Lit (реагує на `Light2D` циркадного світла); додаткові атрибути — у UV1–UV3.

## Розглянуті альтернативи
| Варіант | Плюси | Мінуси |
|---|---|---|
| `LineRenderer` на кожну гілку | Просто | 200 draw calls/об'єктів, погана конусність і стики |
| SpriteShape | Готовий інструмент | Не для деревоподібних графів, важкий |
| Скелетна анімація (2D Animation) | Гнучкі кістки | Надмірно, складно генерувати процедурно |
| Перебудова мешу щокадру | Проста анімація | CPU/GC-вартість, батарея |
| Інстансинг окремих листків (ред. 1) | Деталізація | Не L2: силует «віника», 1 000+ квадів, гірший overdraw; подушки референсу не виходять |
| Подушка = один великий спрайт на `PadId` | Найменше overdraw | Подушка не росте поступово з вузлами, обрізка не «відкушує» шматок; стрибки форми при зміні `PadSize` |
| Подушки через offscreen-RT + композит (метабули/SDF) | Ідеально гладкий об'єднаний контур | +1–2 проходи, RT-пам'ять, складність на слабких GPU |
| Сегмент = окрема стрічка з круглими капами (ред. 1) | Простіше | Злами на стиках, шви UV кори, зайві вершини кап |

## Наслідки
- + 2 draw calls на дерево, ≈ 6 000 вершин разом, перебудова раз на добу/зріз; 0 B GC.
- + Форма і контур читаються як L2: плавна S, комір гілок, Небарі, подушки з темним низом.
- + Сезони, Dormancy, вітер, посуха — без перебудови мешу.
- − Власний mesh-builder, сплайни, сортування пуфів і два Shader Graph — найризиковіша частина Спринту 1 (Spike у PA-103).
- − Overdraw крони 4–5× — головний ризик продуктивності на Android mid-tier при 120 FPS.
- Перевірити (PA-103): Performance-тест перебудови @200 (ціль ≤ 1 мс на mid-tier, 0 B GC); GPU-кадр на референсних пристроях (Xcode GPU capture / Android GPU Inspector) — частка листя; AC20 PA-102S (ширина основи / 2/3 висоти ≥ 4.0) по мешу; скриншот-порівняння з `concept_day` (AC21).

### Відхилення від BALANCE §1.2 [RENDER]
- C1-сплайн — для всіх осей (гілки з droop теж мали б злами 5–15° на стиках), не лише для стовбурного ланцюга.
- `tipWidth = max(дитина, Thickness · TerminalTipRatio)` замість «товщина апікальної дитини» — без «шийки» під тонкою брунькою.
- Вибір спрайта/фаза вітру/підмножина Dormancy — від `Id`, а не від `PadId` (індексу), бо індекс змінюється після `Prune`.
