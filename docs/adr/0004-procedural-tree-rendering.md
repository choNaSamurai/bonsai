# ADR-0004: Процедурний меш гілок уздовж C1-осей + листя подушками з кластерів спрайтів; анімація у вершинному шейдері

- **Статус**: Proposed
- **Дата**: 2026-10-03 · **Ревізія 2**: 2026-10-05 (PA-102S: арт-напрям L2 Painterly — C1-осі, `AttachT`, мальована кора, Небарі, подушки замість інстансу листків; бюджети) · **Ревізія 3**: 2026-10-05 (PA-102P: товсті звивисті корені Небарі з 2 C1-сегментів, подушка = кластер цілих спрайтів (TD-027), ряди, покриття кінчиків `InPad`, бруньки без кори, горщик як масштаб сцени; закрито «Відхилення від BALANCE»; статус ревізії — Proposed)
- **Автор**: Unity Architect, Technical Artist
- **Погоджує**: власник проєкту
- **Пов'язані задачі**: PA-102S, PA-102P, PA-103S, PA-103a, PA-103b, PA-104, PA-105A, PA-305

## Контекст
Оригінал: single-pass `TreeRenderBox`, 4 `drawPath` (яруси товщини), 1 `drawRawAtlas` для листя, zero-alloc буфери, `rain_sheen.frag`, світлячки як частинки. Ціль — 120 FPS без GC.

Ревізія 2: власник затвердив арт-напрям **L2 Painterly** (`Art/Source/Section_0/realism_l2_painterly.jpg`, `A_Concept/concept_day.jpg`): S-подібний стовбур з різкою конусністю і видимим Небарі, ярусні майже горизонтальні гілки з голими внутрішніми частинами, крона — пласкі **подушки-хмарки** з темнішим низом, кора — мальована текстура з м'яким контуром. Прототип PA-102V показав, що «листок на вузол» + діти на кінчику батька дають «віник». BALANCE §1.2 (Proposed) задає правила форми; тут — як це рендерити.

Ревізія 3: порівняння прототипу PA-103S з референсом (`compare_momiji*.png`) показало: Небарі — тонкі прямі «вуса», подушки злипаються в «стос млинців» (2 пуфи на вузол × цілі спрайти-подушки TA), голі кінчики гілочок стирчать за контур. BALANCE §1.3 (Proposed, PA-102P) задає нові правила [RENDER] для коренів (§1.3.3) і подушок (§1.3.4); прототип PA-103S уже перейшов на кластери цілих спрайтів (TD-027). Тут вони закріплюються як рішення для production-рендеру (PA-103a/PA-103b).

## Рішення

### 0. Загальна схема
Дерево = **2 draw calls** у steady-state: (1) меш гілок + коріння, (2) меш листя/пуфів/бруньок/квітів. Обидва — `MeshRenderer` з одним `Mesh` (`MarkDynamic`), перебудова **лише при зміні `TreeGraph.Version`** (ріст раз на добу, зріз, дріт) із преалокованих `NativeArray` через `Mesh.SetVertexBufferData`/`SetIndexBufferData` (0 B GC; за потреби — Burst job). Анімація (вітер, дихання Дзен, посуха, сезони, Dormancy) — лише параметри шейдера; CPU не рухає вершини щокадру.

Вхід перебудови: `ReadOnlySpan<NodeData>` → `TreeShapeAnalysis` → `TreeGeometry` (ADR-0003 §4–§5, Domain, double) → float-вершини. Хіт-тест PA-104 і дріт PA-105B читають ту саму `TreeGeometry`.

### 1. Гілки — меш уздовж C1-осей
- **Осі.** Дерево розбивається на осі: ланцюг вузлів через апікальних дітей (`BranchSide = 0`), що починається з #0 або з будь-якої бічної дитини. Стовбурний ланцюг + вісь крони — одна вісь; кожна первинна/вторинна гілка зі своїми продовженнями — окрема вісь. Кожна вісь — **одна безперервна стрічка** без внутрішніх стиків (немає круглих кап між сегментами осі, немає T-junction-артефактів).
- **Крива осі.** Через стики вузлів — центрипетальний Catmull-Rom → кубічні Безьє-сегменти з узгодженими дотичними (C1). `Curvature` вузла додається поверх як зміщення вздовж нормалі до хорди функцією `b(t) = 16t²(1−t)²` (нульове значення **і похідна** на кінцях → C1 зберігається); амплітуда в t = 0.5 = `0.75 · Curvature · CurvatureOffsetRatio · Length` — збігається з серединою кубічного Безьє PA-102V (BALANCE §1.2.6), тож форма гілок не змінюється відносно прототипу, зникають лише злами. Це застосовується до **всіх** осей, не лише до стовбура (BALANCE §1.2.3 вимагає C1 лише для стовбура — див. «Відхилення»).
- **Кріплення.** Основа бічної осі = точка на кривій батька при `AttachT` (де Кастельжо на сегменті батька). Початок стрічки зсувається назад усередину батька на `0.5 · ширина батька` вздовж власної дотичної → «комір» гілки без щілини; бічна вісь малюється **після** батька (порядок осей = порядок кореневих індексів), тож комір лягає поверх кори батька.
- **Профіль ширини** (BALANCE §1.2.2): `w(t) = lerp(Thickness, tipWidth, t)` уздовж вузла; `tipWidth = max(Thickness(ApicalChild), Thickness · TerminalTipRatio)` (без апікальної дитини — `Thickness · TerminalTipRatio`, 0.45). `max` прибирає «шийку», коли на товстому сегменті з'являється тонка брунька (напр. Фенікс 2.5 на стовбурі 10.8): стрічка дитини перші `JointBlend` = 15% довжини плавно звужується від ширини стику до власного профілю. Кінець осі — напівкругла капа.
- **Небарі — частина мешу гілок** (ред. 3, BALANCE §1.3.3; замінює числа §1.2.4). Будує `NebariBuilder` (Presentation, float, 0 B GC, преалоковані буфери) з `th0 = Thickness(#0)`, `Genome.Seed` і `TreeRenderConfig.Nebari*`; у `TreeGeometry` (Domain) корені **не входять** — їх не можна зрізати чи дротувати, хіт-тест і Pot Lip їх не бачать.
  - **Розширення основи**: `w(y) = th0·(1 + F·e^{−y/(1.5·th0)})`, `F = 0.25 + NebariFlareGain·clamp01((th0 − 4)/20)` (`NebariFlareGain` 0.70 → Д80 F = 0.65) — додаткові перерізи в нижній частині осі #0.
  - **Кількість**: `n = clamp(round(2 + (th0 − 4)/NebariThicknessPerRoot), 2, 7)` (2.2 → 7 з th0 ≥ 13.9). `round` — **від нуля** (`floor(x + 0.5)`), не дефолтний банківський `Math.Round` (у C# `Math.Round(6.5) = 6` → межа 13.9 зсунулась би). `th0` ніколи не зменшується → `n` монотонна, корені не зникають.
  - **Стабільність**: параметри кореня *i* залежать лише від `(Seed, i, salt)` (хеш TD-018, не PCG-потік) і `th0`, **не від `n`** → поява сьомого кореня не зсуває шість наявних. Тому віяло задається **таблицею слотів за індексом**, а не рівномірним розподілом на `n`: азимут `a_i = f_i · NebariFanDeg + hash·NebariFanJitterDeg`, `f = [−0.80, +0.80, −0.45, +0.45, +0.12, −1.00, +1.00]` (75° ± 10°) → при `n ≥ 4` на кожному боці ≥ 2 корені, при `n ≥ 5` один «передній» (|a| ≤ 25°, довжина × `NebariFrontRootScale` 0.6 — ракурс). У 2D азимут дає бік (знак) і горизонтальний виніс (∝ |sin a|, не менше 0.35 — корінь не «зникає» в точку).
  - **Форма**: два кубічні Безьє з **спільною дотичною на стику** (C1). Сегмент 1 стартує з контуру розширення на висоті ≈ 0.15·th0 і йде вниз-назовні під `NebariRootDropDeg` ∈ [35°, 55°] (хеш) нижче горизонталі; стик — на 45–55% довжини; сегмент 2 вигинається до майже горизонталі (0–10° нижче) і закінчується **під верхньою лінією `SoilFront`** — кінець схований мохом. Видима довжина `th0 × [0.9, 1.4]` (парні/непарні індекси — довгий/короткий + хеш).
  - **Звивистість**: зміщення вздовж нормалі `NebariRootWaviness · th0 · sin(2π·s + φ) · 16s²(1−s)²` (s — частка дуги кореня, φ — хеш): обвідна з нульовим значенням і похідною на обох кінцях → C1 на основі й кінці зберігається, на стику сегментів синус гладкий.
  - **Профіль**: основа `th0 × [0.30, 0.42]` (чергування), лінійно до `NebariRootTipRatio` = 0.45 основи на лінії моху; стрічка продовжується під мох ще на 0.5 ширини й закінчується капою — **у видимій частині корінь ніколи не тоншає до 0** (AC6 PA-102P).
  - **Кора коренів**: той самий матеріал і `_BarkTrunk` (`barkAge = 1`), `u` поперек × ширину, `v` = дуга кореня / `BarkTileWorld` зі стартом `hash(Seed, i)`; ink-контур і циліндричне затінення — як у гілок. Корені пишуться в індексний буфер **перед** віссю стовбура → розширення основи перекриває їхні початки (без шва); кінці ховає `SoilFront` (§3).
  - **Поява кореня**: плавна за `NebariRootFadeSec` — Presentation пам'ятає час першої появи кожного з 7 слотів (масив, без алокацій) і передає вершинним атрибутом; шейдер масштабує довжину. Перебудови щокадру немає.
  - Бюджет: 7 × (2 сегменти × 6 перерізів) × 2 + капи ≈ 200 вершин.
- **Кора, UV.** Дві безшовні мальовані текстури в одному матеріалі: `_BarkTrunk` (B2 v2 `bark_trunk_v2`) і `_BarkYoung` (`bark_young_v2`), 512², wrap Repeat, ASTC.
  - `v` = довжина дуги осі / `BarkTileWorld` — неперервна вздовж осі (одна вісь = одна стрічка, без стрибків на стиках); бічна вісь стартує з `v = hash(Id)` → немає однакового візерунка на сусідніх гілках.
  - `u` = позиція поперек ∈ [0, 1] × `w / BarkTileWorld` → ізотропна щільність текселів на товстих і тонких гілках (немає «розтягнутих» тонких пагонів).
  - Бленд trunk ↔ young — вершинний атрибут `barkAge = smoothstep(YoungMaxWidth, TrunkMinWidth, w)` з поправкою на `Order` (ord 0 тяжіє до trunk), інтерполюється вздовж осі → плавний перехід, без швів.
  - Painterly-деталі в шейдері: фальшиве циліндричне затінення за `u` (світло зліва-згори), м'який темний контур біля країв стрічки (як ink-лінія в `concept_day`), антиаліасинг краю через `fwidth` замість MSAA.
- **(ред. 3) Кора в подушках і бруньки** (BALANCE §1.3.4): стрічка `InPad`-вузла з `ord ≥ 2` закінчується на `PadTwigInset = 0.35·PuffRadius` **до** кінчика (кінчик — під листям, голі кінці не стирчать за контур); вузол `Status = Bud` має кору не довшу за `BudBarkMaxLength = 1.5` units (далі — лише спрайт бруньки в меші листя). Обидва правила — лише в mesh-builder, `TreeGeometry` не змінюється (хіт-тест бачить повну довжину).
- **(ред. 3) Калюс** (PA-105A, GDD §4.2): вершини біля місця зрізу (кінчик батька з `LastCutDay ≥ 0`, ADR-0003 rev.3) несуть атрибут «день зрізу»; шейдер кори темнить/затягує зріз за `_GrowthDay − cutDay` (глобальна властивість, раз на добу). Без перебудови мешу; форма й тривалість — PA-105A/TA.
- **Бюджет** (200 вузлів, Д80 без обрізки, адаптивні перерізи: ланцюг 8–10/вузол, гілки 4–6, вторинні 3): ≈ 1 100 перерізів × 2 = 2 200 вершин + ~100 кап кінчиків × 5 + коріння 7 × 12 + розширення основи ~20 → **≈ 3 000 вершин, ≈ 4 500 трикутників**. Преалокація — 8 192 вершини / 12 288 трикутників (worst case 200 × 12 перерізів), індекси `ushort`. Формат вершини ≈ 32 B (pos float3, uv float2, color32, атрибути float3: `barkAge`, `flex`, `windPhase`) → завантаження ≈ 100 КБ на перебудову (раз на добу/зріз).

### 2. Листя — подушки з кластерів цілих спрайтів (ред. 3)
- **Хто несе листя** — лише `IsLeafy` (ADR-0003 §4; ред. 3 — через `InPad`, BALANCE §1.3.4). Стовбур і внутрішні частини гілок голі.
- **Подушка рендеру = компонента `PadId` = кластер цілих спрайтів-подушок** з атласу породи (D5 / дев-арт TA `pads_<species>.png` + `.json`, 9 форм S/M/L з запеченим темним низом і контуром) — рішення TD-027 переходить із прототипу в production і **замінює** «2 пуфи на leafy-вузол» ред. 2 (цілі спрайти-подушки, накладені по 20–40 на подушку, давали «стос млинців»):
  - **Повна подушка** (`PadSize ≥ PadFullNodes`): лінія регресії центрів вузлів подушки (нахил ≤ 0.35); нижній ряд — `ceil(ширина об'єднання / (6·PuffRadius))` спрайтів уздовж лінії з перекриттям ×1.3; вищі ряди — вужчі, поки не покрито висоту об'єднання, але не більше **`PadMaxRowsSide` = 2** для бічних подушок (Kuromatsu — **1**, Yamazakura — 2 з легшими формами) і **`PadMaxRowsDome` = 3** для купола. **Купол** = компонента, що містить вузол осі крони або верхівку стовбурного ланцюга (k4 без апікальної).
  - **Мала подушка** (`PadSize < PadFullNodes`, «пагін не на місці», молоде дерево): по одному малому спрайту на leafy-вузол, без рядів.
  - Розмірний клас — від ширини спрайта (≥ 4.5 / ≥ 2.6 `PuffRadius` → L / M, інакше S); `PuffRadius × LeafScale` і `PadFlatten` — масштаб, не кількість. Варіант і дзеркалення — хеш `(Seed, Id кореня подушки, слот)` (TD-018).
  - **Покриття кінчиків** (AC7 PA-102P): після розкладки рядів кожен кінчик `InPad`-вузла з `LeafScale ≥ 0.5` перевіряється проти «суцільних» еліпсів розставлених спрайтів (еліпс, усередині якого α ≥ 0.5, — поле метаданих атласу від TA); непокритий кінчик отримує додатковий S-спрайт з центром на кінчику (≤ 1 на кінчик, ≤ `PadExtraSpritesMax` = 6 на подушку; переповнення — dev-лог, AC-харнес його ловить).
  - **Тінь-підкладка**: перед подушкою — її ж спрайти, ×(0.30, 0.33, 0.24) кольору, α 0.32, зсув −12% висоти (TD-027) — у тому ж меші й draw call.
  - **Плавність**: кількість спрайтів змінюється лише при перебудові (`Version`); новий спрайт з'являється масштабом через вершинний атрибут «час появи» (як корені), зрізаний — зникає разом із вершинами (падіння піддерева — окремий меш, §3). Зміна `Id` кореня подушки (зріз кореня подушки, злиття двох подушок) перекидає варіанти спрайтів цієї подушки — прийнятно (подушка й так змінила форму).
- **Свіжий приріст**, бруньки (D4), квіти Yamazakura (D3), «свічки» Kuromatsu — квади в **тому ж мешу** й атласі → той самий draw call.
- **Геометрія спрайта**: tight-меш (8–12 вершин за контуром альфи, Unity Sprite Mesh Type = Tight) замість квада → −30…40% прозорих фрагментів. Вузли з `LeafScale < 0.02` не дають ні спрайтів, ні внеску в ширину подушки.
- **Сортування** (один draw call → порядок = порядок індексів, CPU-сортування при перебудові, преалоковані ключі, без алокацій): подушки — за висотою кореня подушки (нижні яруси раніше, апекс останнім, рівні — за `Id`); у подушці — тінь-підкладка, потім ряди знизу вгору, у ряду крайні перед центральними, додаткові S-спрайти покриття й свіжий приріст останніми. Так світлі верхні пуфи перекривають темні низи сусідів, купол апексу лягає поверх. Меш листя — Sorting Layer `Leaves`, вище за гілки (`Tree`) → подушки ховають кінці гілок, як у референсі.
- **Нижня тінь** (`PadUndersideShade`): вершинний атрибут `padLocalY` (−1 низ … +1 верх у межах подушки) → шейдер затемнює низ подушки як цілого. Спрайти TA вже мають запечений темний низ, тож **дефолт ред. 3 — 0** (не подвоювати); параметр лишається для D5, якщо там низ не запечено. Без окремого проходу тіні.
- **Сезони й Dormancy — параметри матеріалу**, без перебудови мешу:
  - `_SeasonTex` (осінній/квітковий лист атласу з тією ж розкладкою) + `_SeasonBlend` 0..1; `_FoliageVisible` 0..1 — частка видимих спрайтів (ред. 3: хеш `(Id кореня подушки, слот)`) (Momiji взимку 0; Dormancy 0.20) за хешем `Id` у вершинному атрибуті; невидимі пуфи **схлопуються у вершинному шейдері** (масштаб 0) → нуль фрагментів, без `discard`;
  - `_Desaturation` (Dormancy 0.40), `_FreshTint` (+15% value за атрибутом `freshness`), `_Wetness` (rain sheen), `_Droop` (посуха, −12°).
  - Глобальні значення сезону/доби — `Shader.SetGlobal*` раз на зміну стану (не щокадру); на дерево — власний екземпляр матеріалу, створений один раз (а не `MaterialPropertyBlock`, який вимикає SRP Batcher), `SetFloat` з кешованими ID властивостей лише при зміні значення.
- **Вітер** — у вершинному шейдері, **спільний HLSL-include** для гілок і листя: зміщення = f(`_WindTime`, позиція якоря, `flex`, `windPhase`). Пуф несе позицію і `flex` точки кріплення (вершини гілки в цій точці мають ті самі значення) → подушка рухається разом зі своєю гілкою + власне легке колихання (±0.8°, 3.5 с — ARCHITECTURE §6.2). `windPhase` — хеш `Id` кореня подушки → подушка гойдається як ціле. Дихання Дзен — масштаб Y×1.015 від основи стовбура в обох шейдерах.
- **До появи арту D5** — плейсхолдер-атлас тієї ж розкладки (3×3), згенерований Editor-скриптом із процедурних плям (еліпс + шум контуру + темний низ). Той самий шейдер і шлях даних, без shader keyword → заміна арту = заміна текстури (TD-020).
- **Бюджет (ред. 3)**: Styled Д80 — 6–7 бічних подушок × 3–5 спрайтів + купол 6–8 ≈ 30–45 спрайтів, з підкладками ×2 ≈ 60–90; Wild Д80 (більше подушок, малі подушки по спрайту на вузол) — до ≈ 150 спрайтів, з підкладками ≈ 300; + до ~40 квадів бруньок/свічок. Tight-меш 10 вершин → **≤ 3 400 вершин** у найгіршому разі (преалокація 6 144 — без змін, запас). Атлас — на породу 1024² ASTC 8×8 (≈ 0.25 МБ + mips), сезонний варіант — ще один; кора 2 × 512² ASTC 6×6 (≈ 0.1 МБ кожна).

### 3. Draw calls сцени з деревом

| Що | Draw calls | Примітка |
|---|---|---|
| Гілки + коріння + розширення Небарі | 1 | одна текстурна пара кори в одному матеріалі |
| Пуфи + бруньки + квіти + свічки | 1 | атлас породи + сезонний атлас |
| Мох/ґрунт поверх коріння (`SoilFront`) | 1 | належить горщику (`PotView`, `PotConfig`), потрібен, щоб коріння «пірнало» в мох; Sorting Layer між `Tree` і `Leaves`. Ред. 3: верхня лінія `SoilFront` — межа видимості кінців коренів (§1) |
| Відрізане піддерево, що падає (0.35 с) | +2 тимчасово | меш з пулу, ARCHITECTURE §6.4 |

Дерево — **2**, з горщиком/фоном/FX — **6–8** на сцену (без UI). SRP Batcher сумісний (один матеріал на меш, властивості через CBUFFER).

### 4. Overdraw і fill rate
Розрахунок ред. 2 (2 пуфи на вузол) на 200 вузлів, Д80 без обрізки, Momiji (найбільші пуфи: r = 9, rx = 11.25, ry = 7.3 units), дерево вписане в ширину портретного екрана (≈ 5 px/unit на 1179 px):
- площа еліпсів пуфів ≈ 260 units² × 240 ≈ 62 тис. units²; площа квадів ≈ 470 units² × 240 ≈ 113 тис.; з tight-мешем ≈ 75 тис.;
- видима площа крони ≈ 13 тис. units² → **глибина перекриття в кроні ≈ 4–5× (піки 6–8 у густих подушках)**;
- відносно екрана (≈ 120 тис. units²): листя ≈ **0.6–0.9 екрана** фрагментів, разом із фоном (1.0), горщиком і гілками ≈ **2.2–2.6× екрана за кадр**.
- iPhone (1179×2556 ≈ 3 MP) @120 FPS ≈ 0.8–0.9 GP/s змішаних фрагментів — у межах для Apple GPU (TBDR, блендинг на чипі). Android mid-tier (2400×1080, Mali-G57/Adreno 6xx) @120 FPS ≈ 0.7 GP/s — на межі; @60 — запас ×2.

**Ред. 3 (кластери спрайтів)**: спрайтів у 3–6 разів менше, але кожен більший; перекриття в ряду ×1.3, між рядами ≈ 30–40%, підкладка α 0.32 під кожною подушкою → очікувана глибина в кроні **≈ 2.5–3.5×** (замість 4–5×), листя ≈ 0.4–0.6 екрана. Це оцінка — **виміряти** в PA-103b (GPU capture, `compare_momiji` Д80/Д120, Wild Д80) до зниження вимог профілю `LowEnd`.

Ризики напівпрозорих пуфів і як знімаємо:
1. **Fill rate** на слабких Android → tight-меш; фрагментний шейдер ≤ 2 вибірки (друга — лише при `_SeasonBlend > 0`), `half`; `discard`/alpha-test не використовуємо (ламає HSR на Apple/PowerVR); профіль `LowEnd`: без тіні-підкладки, на 1 ряд менше (мін. 1), render scale 0.8; `OnDemandRendering` у простої (ARCHITECTURE §6.5).
2. **«Шви» при напівпрозорості цілого шару**: якщо згасати листя глобальною альфою (сезон, Dormancy, зріз), перекриття пуфів стають видимими темнішими плямами. Правило: згасання — **масштабом/розчиненням окремого пуфа**, ніколи не загальною альфою шару; без offscreen-RT (зайвий прохід і пам'ять).
3. **Порядок** у межах одного draw call фіксується при перебудові: вітер не міняє порядок, тож мерехтіння сортування немає; між подушками різних ярусів можливі «неправильні» перекриття при сильному дроті — прийнятно для painterly.
4. **Розмір білда**: кожен атлас 1024² ASTC 8×8 ≈ 0.25–0.35 МБ download; 3 породи × (база + сезон) ≈ 1.5–2 МБ — треба врахувати в бюджеті Android ≤ 25 МБ (baseline 18.2) → якщо тісно, 2048²-джерела D5 ріжуться в атлас 1024² або 512² для S/M форм.

### 4a. Горщик — масштаб сцени (ред. 3)
- Горщик за замовчуванням має **фіксовану** ширину зовнішнього переднього краю `PotConfig.FrontWidthUnits` = **92 units моделі** (BALANCE §1.3.0) і не масштабується під дерево (прибирається `clamp(0.62·W, 60, 170)` прототипу TD-024). Дерево рендериться в units моделі 1:1 — саме відношення H/P, W/P дає пропорції референсу.
- Горщик **косметичний** і в Domain не потрапляє: Pot Lip і основа #0 — у координатах моделі (основа #0 = (0, 0) на лінії ґрунту), `PotConfig` впливає лише на `PotView`/`SoilFront` і кадрування. Де живе конфіг і як кадрується камера — ARCHITECTURE §6.1, TD-030.

### 5. Інше (без змін з редакції 1)

## Розглянуті альтернативи
| Варіант | Плюси | Мінуси |
|---|---|---|
| `LineRenderer` на кожну гілку | Просто | 200 draw calls/об'єктів, погана конусність і стики |
| SpriteShape | Готовий інструмент | Не для деревоподібних графів, важкий |
| Скелетна анімація (2D Animation) | Гнучкі кістки | Надмірно, складно генерувати процедурно |
| Перебудова мешу щокадру | Проста анімація | CPU/GC-вартість, батарея |
| Інстансинг окремих листків (ред. 1) | Деталізація | Не L2: силует «віника», 1 000+ квадів, гірший overdraw; подушки референсу не виходять |
| Подушка = один великий спрайт на `PadId` | Найменше overdraw | Подушка не росте поступово з вузлами, обрізка не «відкушує» шматок; стрибки форми при зміні `PadSize` |
| (ред. 3) 2 пуфи-спрайти на leafy-вузол (ред. 2) | Подушка росте вузол за вузлом | Зі спрайтами TA (цілі подушки з запеченим низом) — 20–40 накладених цілих подушок, «стос млинців», overdraw 4–5×; прототип PA-103S |
| (ред. 3) Корені — пряма стрічка до 0 (ред. 2) | Простіше | Тонкі «вуса» замість кореневої лапи референсу; AC6 PA-102P недосяжний |
| Подушки через offscreen-RT + композит (метабули/SDF) | Ідеально гладкий об'єднаний контур | +1–2 проходи, RT-пам'ять, складність на слабких GPU |
| Сегмент = окрема стрічка з круглими капами (ред. 1) | Простіше | Злами на стиках, шви UV кори, зайві вершини кап |

## Наслідки
- + 2 draw calls на дерево, ≈ 6 000 вершин разом, перебудова раз на добу/зріз; 0 B GC.
- + Форма і контур читаються як L2: плавна S, комір гілок, Небарі, подушки з темним низом.
