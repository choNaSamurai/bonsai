Формули:

$$\text{depthScale}(d) = \max\left(0.1,\ \text{clamp01}\left(1 - \tfrac{d}{D_{max}}\right)^{1.8}\right)$$

$$P_{growth} = P_{base}\left(1 - \tfrac{d}{D_{max}}\right) M_{soil}\, T_{factor}\, \mathbb{I}(N < 200)$$

$$T_{factor} = \text{clamp01}\left(\tfrac{T-5}{18}\right)\left(1 - \text{clamp}\left(\tfrac{T-38}{12}, 0, 0.8\right)\right)$$

$$M_{soil}(W) = \text{clamp01}\left(\tfrac{W - W_{dry}}{W_{opt} - W_{dry}}\right),\quad W_{dry} = 0.10\ (\texttt{SoilConfig.DryThreshold}),\ W_{opt} = 0.40$$

$$\Delta th = (th_{max} - th)\left(1 - e^{-r\Delta t}\right),\quad r = \frac{K_{thick} M_{soil}\,\text{depthScale}}{th_{max}},\quad th_{max} = 24\cdot\text{depthScale}$$

Значення depthScale / $th_{max}$ при $D_{max} = 8$: d0 1.000 / 24.0 · d1 0.786 / 18.9 · d2 0.596 / 14.3 · d3 0.429 / 10.3 · d4 0.287 / 6.9 · d5 0.171 / 4.1 · d6–d8 0.100 / 2.4.

### 1.1. Алгоритм добового росту (`GrowthGrammar`)

Реалізує Gameplay Developer у Domain (PA-102). Усі числа — з `GrowthConfig` / `SpeciesConfig` / `SoilConfig`; кути в Domain — у радіанах (градуси лише в Config).

> **⚑ PA-102S (Proposed, 2026-10-05)**: кроки 5, 6.1, 6.4, посадка і `HasLeaves` змінюються правилами форми бонсаю — див. **§1.2**. Позначка ⚑ нижче = місце зміни; там, де §1.2 і цей розділ розходяться, діє §1.2. Кількість пагонів на добу (6.2–6.3) і погодинна частина — без змін.

**Стан дерева поза вузлами** (зберігається в сейві разом із `TreeGraph`): `GrowthHourCounter` (int, 0..23), `GrowthDayIndex` (int, 0 при посадці), `ShootCredit` (double ≥ 0), `SumGrowthFactor`, `SumMoistureFactor` (double). **Нове поле вузла**: `TargetLength` (double) — пропозиція до ADR-0003 (див. «Залежності» нижче). `HasLeaves` не зберігається: `HasLeaves ≡ Depth ≥ 1 ∧ Status ∈ {Growing, Mature}`. ⚑ Рендер листя — лише для `IsLeafy` (§1.2.5); **нове поле вузла** `AttachT` (§1.2.1).

**Випадковість.** Усі випадкові вибори — через `IRandomSource` (PCG32). Генератор для доби *k*: `Pcg32(seed: SeedGenome.randomSeed, stream: k)`; посадка використовує stream 0, доба росту *k* = `GrowthDayIndex` після інкременту (1, 2, …). Стан RNG не зберігається. `u()` = `NextUInt() / 2^32` ∈ [0, 1). Трикутний розподіл `tri(m, s) = m + s·(u() + u() − 1)` — значення завжди в [m − s, m + s], пік у m.

**Кожна симульована година** (онлайн-тік і офлайн catch-up однаково; не виконується, поки `!OnboardingCompleted` або `IsDormant`):
1. Спочатку `SoilSimulation.SimulateOneHour` (§4) → нове W.
2. `g = M_soil(W) · T_factor(T_години)`; `SumGrowthFactor += g`; `SumMoistureFactor += M_soil(W)`.
3. `GrowthHourCounter++`; якщо `== HoursPerGrowthDay` → `DailyStep()`, лічильник і обидві суми = 0.

**`DailyStep()`** — суворо в такому порядку:
1. `G = SumGrowthFactor / 24`, `M̄ = SumMoistureFactor / 24` (обидва ∈ [0, 1]). `GrowthDayIndex++`. `nebari = (Count ≥ MaxNodes)` — фіксується до спавну.
2. **Розвиток** — для кожного вузла в порядку індексу: `AgeDays++` (календарні доби росту, незалежно від G); `Bud ∧ AgeDays ≥ BudDays → Growing`; `Growing ∧ AgeDays ≥ MatureDays → Mature`. Стовбур (depth 0) завжди `Mature`.
3. **Видовження** — для вузлів зі статусом ≠ Bud: `Length += (TargetLength − Length)·(1 − e^{−ElongationRate·G})`. Bud лишається з `ShootInitialLength`.
4. **Листя** — для `HasLeaves`: `LeafScale = min(1, LeafScale + G / LeafUnfoldDays)`.
5. **Потовщення** — для всіх вузлів формула з §1 з `M_soil = M̄`, `Δt = 1`; для depth 0 при `nebari` — `K_thick × NebariThickeningMultiplier`. Результат клампиться в [th, th_max]. ⚑ Для depth ≥ 1 додатково — стеля конусності `th_cap` (§1.2.2): кламп у [th, max(th, min(th_max, th_cap))]; обхід у порядку індексу (батько вже оновлений).
6. **Спавн пагонів** (лише якщо `Count < MaxNodes` і `G > 0`):
   1. Кандидати: вузли з `Status == Mature`, `Depth < MaxDepth`, кількість дітей `< MaxChildrenPerNode`. Вага `w_i = 1 − Depth_i / MaxDepth`. ⚑ `w_i` використовується **лише для `rate`** (крок 6.2, темп не змінюється); вибір батька — за вагою `s_i = w_i · RoleWeight_i` (§1.2.7). Якщо кандидатів немає — крок 6 завершується, `ShootCredit` не змінюється.
   2. `rate = clamp(P_base · vigor · Σw_i, ShootsPerDayMin, ShootsPerDayMax) · G`, де `vigor` — з `SeedGenome` (0.5–1.5). `ShootCredit += rate`.
   3. `k = min(floor(ShootCredit), ShootsPerDayMax)`; `ShootCredit −= k`.
   4. Повторити *k* разів (зупинка, якщо `Count == MaxNodes` або кандидатів не лишилось; непороджені пагони згорають):
      - ⚑ **8 викликів `u()` завжди** (було 7), навіть якщо частина не використовується (стабільність потоку): `u1` батько, `u2,u3` кут, `u4` сторона (лише вторинні бічні без сусіда — §1.2.1, §1.2.9), `u5` довжина, `u6,u7` кривина, `u8` позиція кріплення `AttachT` (§1.2.1).
      - **Батько**: перелік кандидатів (перераховується перед кожним пагоном) у порядку індексу; обирається перший, де накопичена сума `w` > `u1·Σw`.
      - **Тип**: ⚑ апікальний, якщо в батька немає апікальної дитини (`BranchSide == 0`); інакше бічний у вільний слот (§1.2.1).
      - **Кут** ⚑ (замінено правилами §1.2.3 / §1.2.6 за роллю батька; формула нижче лишається для вторинних бічних і як історія) (`BaseAngle = CurrentAngle`, відносно осі батька): апікальний — `bendBias·ApicalBendScaleDeg + ApicalAngleJitterDeg·(u2 + u3 − 1)`; бічний — `sign · tri(BranchAngleMean, BranchAngleSpread)` з `u2,u3`, де `sign` = протилежний до знака останньої бічної дитини батька, а якщо її немає — `u4 < 0.5 ? −1 : +1`.
      - **Обмеження Pot Lip**: світовий кут = світовий кут батька (сума `CurrentAngle` від кореня) + новий кут; якщо |світовий| > `MaxShootWorldAngleDeg` — клампиться до ±90° і `BaseAngle` перераховується. Отже, кінчик нового пагона ніколи не нижчий за кінчик батька → інваріант `Y ≥ potLipY` зберігається ростом за побудовою.
      - **TargetLength** = `ShootBaseLength · ShootLengthDecay^(d−1) · (1 + ShootLengthJitter·(2·u5 − 1))`, × `ApicalLengthMultiplier` для апікального, ⚑ × `OrderLengthFactor^min(ord, 2)` (§1.2.6).
      - **Curvature** = `tri(0, CurvatureSpread)` з `u6,u7`. ⚑ Стовбурний ланцюг і бічні з |світовим кутом| ≥ 45° — за §1.2.3 / §1.2.6.
      - Новий вузол: `Depth = d_батька + 1`, `Length = ShootInitialLength`, `Thickness = min(ShootInitialThickness, th_max(d))` ⚑ `= max(MinShootThickness, min(ShootInitialThickness, th_max(d), th_cap))` (§1.2.2), ⚑ `AttachT` (§1.2.1), `Status = Bud`, `AgeDays = 0`, `LeafScale = 0`, без дроту. Вставка зберігає топологічний порядок (ADR-0003).
   5. Якщо після спавну `Count == MaxNodes` → `ShootCredit = 0`.
7. `Version++`, якщо щось змінилось (на практиці — щодоби).

**Посадка (`PlantSeed`, stream 0)** ⚑ (18 викликів `u()`: 2 стовбур + 8 лідер + 8 гілочка; кути/позиція гілочки — §1.2.8) — стан, з яким починається онбординг (час заморожено, `DailyStep` не викликається до `OnboardingCompleted`):
- #0 стовбур: depth 0, `Length = TrunkInitialLength`, `TargetLength = TrunkTargetLength`, `Thickness = TrunkInitialThickness`, `BaseAngle = bendBias·TrunkBendScaleDeg` (= `lean`), `Curvature` — за §1.2.8 (`tri(0, TrunkCurvatureJitter)`, 2 виклики `u()`), `Mature`, без листя.
- #1 лідер: апікальна дитина #0 = сегмент k = 1 стовбурного ланцюга; кут і `AttachT = 1` — за §1.2.3 / §1.2.8, 8 викликів `u()` (§1.2.9); `Length = SaplingLeaderLength`, `Thickness = SaplingLeaderThickness`, `Status = Growing`, `AgeDays = SaplingLeaderAgeDays` (стає `Mature` у першому `DailyStep`), `LeafScale = 1`.
- #2 дика гілочка (ціль першого зрізу, GDD §6): бічна дитина #0; слот, сторона, `AttachT`, світовий кут і `Curvature` — **лише за §1.2.8** (`SaplingTwigAttachT`, `SaplingTwigWorldAngleDeg`; `u4` не використовується); 8 викликів `u()` (§1.2.9); `Length = SaplingTwigLength`, `Thickness = SaplingTwigThickness`, `Status = Growing`, `AgeDays = SaplingTwigAgeDays`, `LeafScale = 1`.
- Після онбордингового зрізу: N = 2 (стовбур + лідер). Лічильники росту = 0; перший `DailyStep` — через 24 год після `OnboardingCompleted`.

**Фенікс** ⚑ (`AttachT = 1`, товщина ≤ `th_cap`; далі ланцюг росте за §1.2.3): якщо після `Prune` `Count == 1` — одразу (не чекаючи `DailyStep`) додається апікальна дитина стовбура: `PhoenixBud*`, `Status = Bud`, `AgeDays = 0`, кут `bendBias·ApicalBendScaleDeg`, `Curvature = 0`, `TargetLength = ShootBaseLength·ApicalLengthMultiplier`; без RNG. Стовбур сам завжди лишається кандидатом (Mature, depth 0), тож дерево не застрягає й без Фенікса.

**Офлайн / Dormancy**: перші ≤ 168 год офлайну — ті самі погодинні кроки (≤ 7 `DailyStep`); у Dormancy лічильники заморожені, росту немає (пагони пробудження — §9.5, окрема задача).

⚑ Після PA-102S таблицю темпу треба **перевиміряти** (вибір батька змінює розподіл глибин → Σw): допуск ±15% (AC10 PA-102); якщо виходить за межі — підстроюється лише `BaseGrowthProbability` (див. §1.2.10).

**Вимірювані AC для QA (PA-102)**:
- Один і той самий геном + однакова погодинна історія → побітово однаковий `TreeSnapshot` (онлайн-тіки ≡ офлайн catch-up) **в межах одного білда й платформи** (ADR-0003, рівень A). Між платформами/рантаймами (Editor ↔ IL2CPP ARM64 ↔ x64) гарантується лише та сама **структура** (кількість вузлів, батьки, сторони, слоти); неперервні значення — з допуском 1e-9 відносно (рівень B). `#dna=` передає геном, а не дерево.
- При G = 1 за добу народжується 1–3 пагони; при будь-якому G — ≤ `ShootsPerDayMax`; при W < 0.10 увесь день — 0 пагонів і 0 видовження.
- `Count ≤ MaxNodes` завжди; при `Count == MaxNodes` нових вузлів немає, `ShootCredit == 0`, потовщення стовбура ×3.
- Жоден вузол не має `Depth > MaxDepth`; жоден новий пагін не має |світового кута| > 90°.
- Кут нового бічного пагона (± до клампу 90°): вторинний — відносний ∈ [`BranchAngleMean` − `Spread`, `Mean` + `Spread`]; первинний — світовий за `PrimaryAngle*` (§1.2.6); гілочка посадки — §1.2.8; товщина ≤ $th_{max}(d)$; без NaN.
- Сценарій G = 1, vigor 1, seed з тест-фікстури: N(Д31) ≥ 50, N(Д47) ≥ 100, N ≤ 200 і досягає 200 не раніше Д66.
- Після посадки N = 3, гілочка #2 — бічна дитина стовбура depth 1; після її зрізу N = 2, після зрізу лідера — Фенікс (N = 2, Bud).

**Залежності**: `TargetLength` у `NodeData` і нові поля стану дерева — зміна ADR-0003 / сейву (Unity Architect); `CurvatureOffsetRatio` — рендер PA-103 (Gameplay Dev / Technical Artist); `vigor` і `bendBias` стартових насінин до PA-205 — 1.0 і 0.0.

### 1.2. Форма бонсаю (PA-102S, **Proposed**)

> Статус: **Proposed** (Game Designer, 2026-10-05) — чекає погодження власника; після «так» Gameplay Developer переносить у `GrowthConfig` / `SpeciesConfig`, рендер-параметри — у `TreeRenderConfig` / `FoliageConfig` (PA-103). Ціль — референс L2 Painterly (`Art/Source/Section_0/realism_l2_painterly.jpg`, `A_Concept/concept_*.jpg`): S-подібний стовбур з різкою конусністю, видимий Небарі, 6–8 ярусних майже горизонтальних гілок з чергуванням сторін, листя пласкими «подушками» на кінцях гілок і куполом на апексі; голі внутрішні частини гілок.
> **⚑P PA-102P (§1.3, Proposed)** замінює: довжини стовбурного ланцюга й осі крони, амплітуди S і нахил #0 (§1.2.3), сторони й порядок слотів ланцюга (§1.2.1 крок 4), роль «Верхівка стовбура» (§1.2.7), `IsLeafy`/ролі Pad-Interior (§1.2.5, §1.2.7 — `InPad` замість `TipDistance`), довжину продовжень гілок (§1.2.6), числа Небарі (§1.2.4); додає бек-бадінг (`LastCutDay`) і стилізацію moyogi.
> Позначки: **[MODEL]** — зберігається/змінюється в Domain (`TreeGraph`, `DailyStep`), впливає на детермінізм і сейв; **[MODEL-derived]** — чиста функція від `TreeGraph` у Domain (`TreeShapeAnalysis`, не зберігається, 0 GC, тестується EditMode); **[RENDER]** — лише PA-103 (меш, шейдер, листя), Domain не змінює.
> Стовпи: дерево без обрізки — «дика заготовка» (зайві яруси, довгі «ноги» гілок, внутрішні пагони), але силует уже читається як бонсай; секатор і дріт доводять його до референсу за 2–4 тижні 1–2 зрізами на день.

#### 1.2.0. Терміни **[MODEL-derived]**

Обчислюються одним прямим (батько → дитина) і одним зворотним проходом по топологічному масиву (ADR-0003), O(n), n ≤ 200.

| Термін | Визначення |
|---|---|
| `ord(i)` (порядок гілки) | `ord(0) = 0`; `ord(i) = ord(parent) + (BranchSide_i ≠ 0 ? 1 : 0)` — скільки бічних відгалужень на шляху від кореня |
| **Стовбурний ланцюг** (trunk chain), індекс `k` | `ord = 0 ∧ Depth < TrunkChainSegments`; `k = Depth` (k = 0 — вузол #0, k = 1 — лідер, …) |
| **Вісь крони** (crown axis) | `ord = 0 ∧ Depth ≥ TrunkChainSegments` — продовження стовбура над останнім сегментом, формує купол апексу |
| `ordEff(i)` | `ord(i)`, але для осі крони = 1 |
| **Первинна гілка** (ярус, tier) | бічна дитина вузла стовбурного ланцюга |
| `TipDistance(i)` | 0, якщо дітей немає; інакше `1 + min(TipDistance(дитина))` (зворотний прохід) |
| **Внутрішній вузол гілки** | `ordEff ≥ 1 ∧ TipDistance > PadDepth` |
| `TierPhase` | `(randomSeed & 1) == 0 ? +1 : −1` — з геному, **без RNG** і без збереження |
| Знаки | світовий кут від вертикалі, **+ = CCW (вліво)** — як `TreeGraph.WorldAngle` і `dir = (−sin θ, cos θ)` у PA-102V; `BranchSide` = знак відносного кута бічного пагона; `sgn(0) = +1` |
| `lean` | `bendBias · TrunkBendScaleDeg` — нахил вузла #0 (як у §1.1) |

#### 1.2.1. Точка кріплення гілок — `AttachT` **[MODEL]** ⚑P (сторони й порядок слотів ланцюга — §1.3.2)

**Нове поле вузла** `NodeData.AttachT` (double ∈ [0, 1], зберігається; пропозиція до ADR-0003 / сейву ADR-0008): частка довжини батька, де починається пагін. Позиція рухається разом з видовженням батька (`AttachT` відносна). Відсутнє в старих даних → 1.0.

| Параметр | Значення | Config |
|---|---|---|
| `AttachT` апікального пагона | 1.0 (завжди на кінчику) | — (константа правила) |
| Бічні слоти звичайного батька (slot0 / slot1) | 0.45 / 0.85 | `GrowthConfig.LateralSlotT0`, `LateralSlotT1` |
| Бічні слоти вузла #0 (основа стовбура) | 0.70 / 0.95 (⚑Q slot0 → **0.78**, §1.4.1; ⚑R → **0.70**, §1.5.3) | `GrowthConfig.TrunkBaseSlotT0`, `TrunkBaseSlotT1` |
| Розкид позиції в слоті | ±0.04 (рівномірний, `u8`) | `GrowthConfig.AttachTJitter` |
| Кламп `AttachT` бічного | [0.05, 0.97] | `GrowthConfig.AttachTMin`, `AttachTMax` |
| Мін. відстань між бічними одного батька | ≥ 0.17 (звичайний ≥ 0.32) — **випливає з чисел вище**, окремо не перевіряється в коді | — (AC) |
| Бічних слотів на вузол | 2 (= `MaxChildrenPerNode` − 1 апікальний) | `MaxChildrenPerNode` (без змін) |

Правило (замінює «Тип» і «знак» кроку 6.4 §1.1):
1. Якщо в батька немає апікальної дитини (`BranchSide == 0`) → **апікальний**, `AttachT = 1`.
2. Інакше — **бічний** у перший вільний слот `s ∈ {0, 1}`. Слот існуючої бічної дитини: `s = AttachT < (SlotT0 + SlotT1)/2 ? 0 : 1` (для #0 межа 0.825, інакше 0.65).
3. `AttachT = clamp(SlotT_s + AttachTJitter·(2·u8 − 1), AttachTMin, AttachTMax)`.
4. **Сторона**:
   - батько в **стовбурному ланцюгу** → `side = TierPhase · (s == 0 ? −1 : +1)`. Отже на кожному сегменті нижній слот завжди з одного боку, верхній — з протилежного, і по висоті стовбура яруси чергуються Л/П/Л/П незалежно від порядку народження; `u4` не використовується;
   - інакше (гілка, вісь крони) — як у §1.1: протилежно до існуючої бічної дитини, якщо її немає — `u4 < 0.5 ? −1 : +1`.
5. Після обрізки слот звільняється і заповнюється заново за тими ж правилами (позиція — у тому ж слоті, з новим `u8`).

Ярусність з чисел (стовбурний ланцюг без дроту, довжини сегментів 48 / 36 / 30.6 / 26 / 22): яруси на висотах ≈ 34 і 46 (#0), 65 і 79 (лідер), 98 і 110 (k2), 127 і 137 (k3), 150 і 160 (k4) — до 10 ярусів з кроком 10–19 units; нижній ярус ≈ 20% висоти стовбурного ланцюга. «Зайві» яруси (референс має 6–7) — природна ціль секатора.

#### 1.2.2. Конусність (taper) **[MODEL]** + профіль **[RENDER]**

`Thickness` вузла = товщина (діаметр) **в його основі**. Товщина батька в точці `t` уздовж нього (модельна апроксимація):

$$th_{at}(p, t) = th_p\,\bigl(1 - (1 - \texttt{SegmentTipTaper})\,t\bigr)$$

Стеля для вузла з depth ≥ 1:

$$th_{cap}(i) = R_i \cdot th_{at}(parent, AttachT_i),\quad R_i = \begin{cases}\texttt{ApicalThicknessRatio}, & \text{апікальний}\\ \texttt{LateralThicknessRatio}, & \text{бічний}\end{cases}$$

| Параметр | Значення | Config |
|---|---|---|
| Звуження сегмента до кінчика | 0.70 | `GrowthConfig.SegmentTipTaper` |
| Апікальний / батько в точці кріплення | ≤ 0.90 (тобто ≤ 0.63 × основи батька); ⚑Q для апікальних дітей вузлів `ord = 0` — `TrunkChainTaperRatio` 0.75 × основи батька і `th_max` від половинної глибини (§1.4.1) | `GrowthConfig.ApicalThicknessRatio` |
| Бічний / батько в точці кріплення | ≤ 0.50 (⚑Q бічні діти вузлів `ord = 0` — `PrimaryThicknessRatio` 0.38, §1.4.3) | `GrowthConfig.LateralThicknessRatio` |
| Мін. товщина нового пагона | 0.30 units (перемагає `th_cap`, щоб пагін був видимий і клікабельний) | `GrowthConfig.MinShootThickness` |
| Рендер: товщина кінчика вузла `tipWidth` | `max(Thickness(апікальна дитина), Thickness × 0.45)`; дитини немає → `Thickness × 0.45` (без «шийки» під тонкою брунькою, напр. Фенікс 2.5 на стовбурі 10.8) | `TreeRenderConfig.TerminalTipRatio` **[RENDER]** |
| Рендер: плавний перехід на стику осі | перші 15% довжини апікальної дитини ширина плавно звужується від `tipWidth` батька до власного профілю | `TreeRenderConfig.JointBlend = 0.15` **[RENDER]** (ADR-0004) |

- Крок 5 `DailyStep`: `th_new = clamp(th + Δth, th, max(th, min(th_max(d), th_cap)))` — ніколи не зменшується (старі/відредаговані дані не «худнуть»). Обхід у порядку індексу → `th_cap` рахується від уже оновленого батька.
- Новий пагін: `Thickness = max(MinShootThickness, min(ShootInitialThickness, th_max(d), th_cap))`.
- **Узгодження з ТЗ**: формула `Δth` і `th_max = 24·depthScale` (ТЗ 3.1.1) не змінюються; `th_cap` — лише **додаткова** верхня межа для depth ≥ 1. Вузол #0 обмежений тільки `th_max(0) = 24`, Небарі ×3 (`NebariThickeningMultiplier`) діє як раніше — тож після 200 вузлів основа товщає, а стелі решти лишаються пропорційними → конусність з віком лише зростає.
- [RENDER] ширина вздовж вузла: `w(t) = lerp(Thickness, tipWidth, t)`, `tipWidth` — з таблиці вище; апікальна дитина перші `JointBlend` довжини переходить від `tipWidth` батька до власного профілю (ADR-0004 §1); бічна дитина стартує з власної `Thickness` (видимий «комір» гілки). Модельних полів і стель `th_cap` це не змінює.

Перевірка (G = 1, M = 1, `r = K_thick/24 ≈ 0.0104`/добу однаковий для всіх depth; лідер народжений при посадці, k2 ≈ Д2, k3 ≈ Д9, k4 ≈ Д15):

|---|---|---|---|---|---|---|---|---|
| Д40 | 10.8 | 6.8 (стеля; природно 7.5) | 4.3 (стеля; 5.3) | 2.7 (стеля; 3.6) | 1.7 (стеля; 2.4) | k2 @ t 0.80 → 3.3 | **3.3×** | 15.3 / 3.3 = **4.7×** |
| Д80 | 15.3 | 9.6 | 6.1 | 3.8 | 2.4 | k2 @ t 0.80 → 4.6 | **3.3×** | 23.4 / 4.6 = **5.1×** |
| Первинна гілка на #0 (slot0, Д40) | th_at = 8.5 | — | — | — | — | гілка = 4.3 (стеля; природно 6.7) | гілка / стовбур у точці = 0.5 | — |

Коли стелі «вмикаються», відношення основа / 2/3 висоти структурно ≈ 3.3 (= 1 / (0.63² · 0.76)); референс L2 ≈ 2.5–3× без розширення кореня, ≈ 4–5× з ним.

#### 1.2.3. Форма стовбура — S-вигини (moyogi) **[MODEL]** + сплайн **[RENDER]** ⚑P (числа — §1.3.1)

Апікальний пагін вузла стовбурного ланцюга (новий сегмент `k ≥ 1`) отримує **цільовий світовий кут**:

$$\theta_k = lean + TierPhase\cdot(-1)^k \cdot A_k + \texttt{TrunkSwayJitterDeg}\cdot(u2 + u3 - 1),\quad A_k = \texttt{TrunkSwayDeg}\cdot(1 + |bendBias|)\cdot \texttt{TrunkSwayDecay}^{\,k-1}$$

`BaseAngle = θ_k − WorldAngle(батько)` (з поточним кутом батька, тобто з урахуванням дроту), потім кламп Pot Lip ±90° як у §1.1. Те саме правило для лідера при посадці (k = 1).

| Параметр | Kuromatsu | Momiji | Yamazakura | Config |
|---|---|---|---|---|
| Амплітуда вигину `TrunkSwayDeg` | 14° | 9° | 12° | `SpeciesConfig.TrunkSwayDeg` |
| Згасання амплітуди вгору | 0.85 / сегмент | ← | ← | `GrowthConfig.TrunkSwayDecay` |
| Розкид кута сегмента | ±3° (трикутний, `u2,u3`) | ← | ← | `GrowthConfig.TrunkSwayJitterDeg` |
| Сегментів стовбурного ланцюга | 5 (k = 0…4) | ← | ← | `GrowthConfig.TrunkChainSegments` |
| `Curvature` сегментів ланцюга (і #0) | `tri(0, 0.10)` (`u6,u7`; для #0 — 2 виклики посадки) | ← | ← | `GrowthConfig.TrunkCurvatureJitter` |
| Вісь крони: апікальний кут | `lean + ApicalAngleJitterDeg·(u2+u3−1)` (купол над останнім сегментом) | ← | ← | `ApicalAngleJitterDeg` (без змін) |

- Чергування гарантоване: `A_4 ≥ 9·0.85³ ≈ 5.5° > 3°` розкиду → `sgn(θ_k − lean) = TierPhase·(−1)^k` для k = 1…4 (якщо гравець не міняв кути дротом).
- `bendBias` (−0.6…+0.6): нахил основи (`lean`, як раніше) і драматизм S (амплітуда ×1.0…×1.6). Kuromatsu при |bendBias| = 0.6: `A_1 = 22.4°` — у межах Pot Lip.
- `ApicalBendScaleDeg` тепер використовується лише Феніксом.
- [RENDER] **кожна вісь** дерева (ланцюг вузлів через апікальних дітей: стовбурний ланцюг + вісь крони — одна вісь; кожна первинна/вторинна гілка зі своїми продовженнями — окрема) малюється як **C1-неперервний сплайн** через вузли-стики (центрипетальний Catmull-Rom → Безьє з узгодженими дотичними) — плавна S стовбура і плавна арка гілок з `BranchDroop` замість зламів 5–15° на стиках; `Curvature` додається поверх зі збереженням C1 (форма середини сегмента — як кубічний Безьє PA-102V). Бічна вісь стартує від кривої батька за `AttachT` з «коміром» (C1 на стику з батьком не потрібен). Деталі — ADR-0004 §1. Модель (кути, `Curvature`) не змінюється.

#### 1.2.5. Листя подушками (foliage pads) **[MODEL-derived]** + **[RENDER]** ⚑P (`IsLeafy` — §1.3.4)

**Хто несе листя** (замінює рендер «листя на кожному вузлі»):

$$IsLeafy(i) = HasLeaves(i) \wedge \bigl[(\text{стовбурний ланцюг} \wedge \text{дітей немає}) \vee (ordEff \ge 1 \wedge TipDistance \le PadDepth)\bigr]$$

- Стовбур і внутрішні частини гілок — **голі** (як у референсі); листя лише на зовнішніх `PadDepth` рівнях кожної гілки. Молодий лідер без дітей — з листям (саджанець читається як рослина).
- **Подушка** = компонента зв'язності `IsLeafy`-вузлів (ребро батько–дитина, обидва leafy). `PadId` = найменший індекс у компоненті (детерміновано; ідентифікатор **лише для аналізу в межах одного снапшота** — після `Prune` індекси компактуються і `PadId` змінюється). Візуальні хеші (варіант спрайта пуфа, фаза вітру, підмножина Dormancy, `v`-зсув кори) — від стабільного `NodeData.Id` (для подушки — `Id` її кореня), хеш `(randomSeed, Id, salt)` (TD-018). Розмір подушки `PadSize` = кількість вузлів; повна подушка — `PadSize ≥ PadFullNodes`.
- `LeafScale` (§1.1 крок 4) лишається в моделі для всіх вузлів і визначає розмір «пуфа», тож вузол, що став leafy після обрізки, одразу показує листя.

- **Kuromatsu**: вічнозелена; бер–тра пагони `Growing` малюються як світлі вертикальні «свічки» `#9CCC65` над подушкою.
- **Yamazakura**: 14–21 доба навесні подушки вкриті пуфами цвіту (`FlowerStage`), листя відростає після.

**Dormancy [RENDER]**: видно лише `DormancyFoliageFraction = 0.20` пуфів (підмножина за хешем `Id`), знебарвлення 40% (`DormancyDesaturation`), кістяк і мох — як `concept_dormancy`. Модель не змінюється (інваріант §9.5).

**Обрізка [MODEL-derived]**: після `Prune` `TipDistance` перераховується → вузли ближче до стовбура стають leafy, подушка «відступає» до гілки і ущільнюється; зрізаний батько стає кінцевим → наступний пагін найімовірніше саме там (§1.2.7, «бек-бадінг»). Зріз первинної гілки прибирає подушку цілком.

**Ціль для секатора (що бачить гравець без жодних маркерів, Calm UI)**:
1. **Дика гілочка** саджанця (§1.2.8) — низько, круто вгору, одна.
2. **Внутрішні пагони** — поодинокі пучки на голій внутрішній частині гілки (народжені від внутрішнього вузла, вага `InteriorWeight`); окрема дрібна подушка «не на місці».
3. **«Ноги» гілок** — без обрізки подушка відповзає від стовбура на кінець довгої голої гілки; світлий свіжий приріст стирчить за контур.
4. **Зайві яруси** — до 10 первинних гілок проти 6–7 у референсі; два яруси майже на одній висоті.

#### 1.2.9. Детермінізм і RNG **[MODEL]**

- Кожен пагін (`DailyStep` 6.4 і посадка): **рівно 8 викликів `u()`** у порядку `u1` батько · `u2,u3` кут (трикутний/розкид за роллю) · `u4` сторона (лише вторинні бічні без сусіда) · `u5` довжина · `u6,u7` кривина · `u8` `AttachT` (лише бічні). Невикористані — все одно витягуються.
- Посадка (stream 0): 2 (стовбур) + 8 (лідер) + 8 (гілочка) = **18** викликів.
- `TierPhase` — біт `randomSeed`, без RNG. Хеші рендеру (коріння, підмножина Dormancy) — окрема хеш-функція `(randomSeed, Id, salt)`, не PCG-потік.
- Наслідок: той самий seed дає **інше** дерево, ніж у PA-102 (зсув потоку з 7 на 8 викликів) — фікстури снапшотів перегенеровуються; сейвів у гравців ще немає.
- Ролі, `TipDistance`, `th_cap` — лише `+ − × ÷` і порівняння над даними графа → топологія детермінована так само, як у PA-102.

| Верхівка, затримка триває, є вільний бічний слот | немає апікальної, `AgeDays < 6 + 3k` | 1.5 `TierWeight` | бічний (ярус) |
| Верхівка, затримка триває, слотів немає | — | **0** (лишається кандидатом для `rate`, не обирається) | — |

#### 1.3.4. Подушки — окремі яруси з повітрям **[MODEL-derived]** + **[RENDER]** (замінює `IsLeafy` §1.2.5)

**Нове визначення зони подушки** (вирішує AC10/AC12 PA-102S — `TipDistance = min` по дітях робив основу листяною через будь-яку коротку бічну):

$$AxisRemain(i) = \begin{cases}0, & \text{апікальної дитини немає}\\ 1 + AxisRemain(\text{апікальна дитина}), & \text{інакше}\end{cases}\quad(\text{зворотний прохід})$$

$$InPad(i) = ordEff(i) \ge 1 \wedge \bigl(AxisRemain(i) < PadDepth \ \vee\ InPad(parent(i))\bigr)\quad(\text{прямий прохід})$$

$$IsLeafy(i) = HasLeaves(i) \wedge \bigl[InPad(i) \vee (\text{стовбурний ланцюг} \wedge \text{дітей немає})\bigr]$$

- Тобто на **кожній осі** гілки листя несуть лише її останні `PadDepth` вузлів **і все, що від них відходить**; внутрішня частина осі — гола незалежно від коротких бічних пагонів.
- **Внутрішній вузол** = `ordEff ≥ 1 ∧ ¬InPad`; **внутрішній пагін** = бічний, чий батько внутрішній: його власний кінчик `InPad` → окрема маленька подушка «не на місці» (ціль секатора, AC12).
- Ролі §1.2.7: «Подушка» = `InPad`, «Внутрішній вузол» = `¬InPad` (замість `TipDistance ≤ PadDepth`). `TipDistance` лишається в аналізі (інші споживачі), для листя/ролей не використовується.
- `PadDepth` без змін: Kuromatsu 1 · Momiji 2 · Yamazakura 2.

**Довжини в подушці** (компактні подушки замість «ніг»):

| Параметр | Було | Стало | Config |
|---|---|---|---|
| Апікальне продовження гілки (ordEff ≥ 1, не вісь крони) | × `ApicalLengthMultiplier` 1.2 | × **`BranchApicalLengthMultiplier = 0.60`** (⚑Q поточне 0.45, TD-031, §1.4.9) (вісь ланцюга/крони — 1.2 без змін) | `GrowthConfig.BranchApicalLengthMultiplier` (новий) |

Momiji первинна з #0: 21 (гола) → продовження 10.7 → 9.1 (подушка); з k4: 11.0 → 5.6 → 4.8. Досяжність від осі стовбура: нижні яруси ≈ 37 + подушка → зовнішній край ≈ 45–55 units; верхні ≈ 20 + подушка ≈ 30–35 → силует-трикутник, **W ≈ 100–110** (ціль 106).

**Повітря між ярусами (перевірка)**: ярус #0 slot0 на 26.6 → центр подушки ≈ 42, подушка ≈ 35–49; наступний ярус того ж боку (k1 slot1) на 54.8 → подушка ≈ 63–77 → **зазор ≈ 14 units** (референс ≈ 13). Сусідні яруси протилежних боків розділені стовбуром (внутрішній край подушки ≈ 8 units від осі).

**[RENDER] (PA-103S прототип → PA-103b)**:
- Подушка рендеру = компонента `PadId`; бічна подушка — ≤ **2** ряди спрайтів (`FoliageConfig.PadMaxRowsSide = 2`), купол — ≤ **3** (`PadMaxRowsDome = 3`); купол = компонента, що містить вісь крони або верхівку ланцюга.
- **Покриття кінчиків**: кожен кінчик `InPad`-вузла з `LeafScale ≥ 0.5` лежить усередині силуету своєї подушки (альфа ≥ 0.5); кора `InPad`-вузлів з `ord ≥ 2` закінчується **всередині** подушки (стрічка обрізається на `PadTwigInset = 0.35·PuffRadius` до кінчика). Голі кінці не стирчать за контур.
- Брунька (`Status = Bud`) — спрайт бруньки, без смужки кори довшої за `BudBarkMaxLength = 1.5` units.

#### 1.3.5. Бек-бадінг після зрізу **[MODEL]** (вирішує AC11 PA-102S)

**Нове збережуване поле вузла** `NodeData.LastCutDay` (int; `GrowthDayIndex` останнього зрізу **дитини** цього вузла; −1 = не було — дефолт для нових вузлів і старих даних, як `AttachT` у TD-022; пропозиція до ADR-0003 rev.3 / сейву ADR-0008 — **Unity Architect**). Те саме поле дає **калюс** на місці зрізу (GDD §4.2: «з часом темніє») → `CallusAge = GrowthDayIndex − LastCutDay` для рендеру — окремий стан не потрібен.

- `Prune(node)`: батькові зрізаного вузла завжди `LastCutDay = GrowthDayIndex` (і на стовбурі — для калюсу).
- [MODEL-derived] `BackBudDist(i)` = мін. кількість ребер від `i` вниз (до нащадків, включно з `i`) до вузла зі «свіжим» зрізом (`LastCutDay ≥ 0 ∧ GrowthDayIndex − LastCutDay < BackBudDays`); зворотний прохід O(n). Вхід аналізу — `GrowthDayIndex`.
- Вибір батька: `s_i = w_i · RoleWeight_i · (BackBudDist(i) ≤ BackBudRadiusEdges ∧ ord(i) ≥ 1 ? BackBudWeightMultiplier : 1)`. Вузли стовбурного ланцюга й осі крони не підсилюються (зрізаний ярус не відростає «сам», купол не витягується).
- `rate` (Σw) **не змінюється** → темп росту той самий; RNG — без змін.

| Параметр | Значення | Config |
|---|---|---|
| Тривалість «пробудження бруньок» | 14 діб росту | `GrowthConfig.BackBudDays` |
| Радіус | 2 ребра від місця зрізу | `GrowthConfig.BackBudRadiusEdges` |
| Множник ваги | ×6.0 | `GrowthConfig.BackBudWeightMultiplier` |

Перевірка (Д40, ~60 кандидатів, Σs ≈ 30): місце зрізу + 2 предки ≈ 0.5·1.0·6 + 0.5·1.0·6 + 0.56·0.25·6 ≈ 6.8 → ≈ 19% усіх пагонів дерева на добу йдуть у зону зрізу; у межах гілки (власна вага ≈ 4) частка біля зрізу ≈ (6.8 + 1) / (4 + 6.8) ≈ **70% ≥ 50%** (AC11). Наслідок для гри: кожен зріз кінчика **ущільнює** подушку (рамифікація) — видимий сенс зрізу.

#### 1.3.6. Детермінізм, RNG, темп **[MODEL]**

- Кількість викликів **не змінюється**: пагін — рівно 8 `u()` (`u5` для сегментів ланцюга тепер дає `TrunkSegmentJitter` замість `ShootLengthJitter`; `u2,u3` для бічних осі крони — `CrownLateralAngle*`); посадка — 18. Порядок потоку той самий.
- Нові правила — без RNG: затримка (ціле `AgeDays`), сторони ярусів (`TierPhase`, k), нахил #0, бек-бадінг (цілі `LastCutDay`/`GrowthDayIndex`), `AxisRemain/InPad`.
- Той самий seed дає **інше** дерево, ніж у PA-102S (інші довжини/кути/ролі) → фікстури снапшотів перегенеровуються; сейвів у гравців немає.
- **Темп**: формула `rate` і множина кандидатів — без змін. Затримка стовбура лише перерозподіляє ранні пагони з апікальних на яруси; бек-бадінг діє тільки після зрізу. Очікування: таблиця §1.1 у межах ±15% без зміни `BaseGrowthProbability`; якщо ні — GD змінює лише `BaseGrowthProbability` (як TD-021).
- Біомаса менша (коротші довжини) — на кількість вузлів і потовщення не впливає.

#### 1.5.9. AC-визначення, що змінюються ⚑R (решта §1.4.0 — без змін)

- **Лінія відліку** — `y_rim` для всіх висот (§1.5.1); AC6 — пороги §1.4.0 без змін, `w(0.02H)` — силует з коренями, `w(≥ 0.06H)` — меш стовбура.
- **Вигини** (нове, доповнює AC9): «виразний вигин» = локальний екстремум відхилення центральної лінії (C1, 64 точки) від хорди основа → кінець k4 з амплітудою ≥ 0.03 H; медіана кількості **∈ [2, 4]**; розмах медіана **∈ [0.09, 0.15] H**; нерівність: відношення найбільшої до найменшої амплітуди виразних вигинів ≥ 1.25 у ≥ 70% сидів.
- **Окремі подушки**: ≥ 80% сидів — рівно 6 бічних компонент маски листя (Д80…Д120, кожен день) — тепер окремий AC, а не лише умова AC1.
- **Корені** (нове): старт верхнього кореня над `y_rim` ∈ [0.025, 0.05] H; товщина кореня в основі / th0 ∈ [0.40, 0.58]; видимість — як AC8 PA-102Q.

#### 1.5.10. Детермінізм, RNG, темп ⚑R

- **`u()`**: рівно 8 на пагін, 18 на посадку — без змін, порядок той самий. Нова «випадковість» без RNG: `h_k` — хеш `(randomSeed, k, "SWAY")` (не PCG-потік, як корені); `TrunkSwayProfile`, `Bow`, `PadTierDecayCompensation`, `DomeLateralWeight` — арифметика над конфігом і графом; компенсація досягу (§1.5.4 б) — `Sin/Tan` над `TargetLength` і кутами, вже збереженими в графі (детермінізм рівня A в межах білда; рівень B — лише неперервні довжини в 1e-9, структура та сама).
- **Темп**: `rate` і множина кандидатів не змінюються; `DomeLateralWeight` лише перерозподіляє вибір (як ролі §1.2.7); довжини подушок змінюють біомасу, не кількість вузлів. Очікування — таблиця §1.1 у ±15%; якщо ні — лише `BaseGrowthProbability` (рішення GD). Висота H20/H80: обидва кінці знижуються на ≈ 4%, відношення ≈ 0.70 (у [0.55, 0.75]).
- **Сейв**: нових збережуваних полів **немає**; `GrowthRules.Version` 3 → **4**, фікстури перегенеровуються.
- **Wild**: правила [MODEL] діють і на дике дерево (верхні подушки більші, S виразніший, купол раніше) — Wild може відрізнятися від еталона; S8 — лише Styled. Wild H80/P ≤ 1.9 і «яруси 6–7 ≥ 90%» — регресія.
- **Chokkan** (σ 0): профіль, нерегулярність, `Bow`, скручування кори множаться на σ → 0; `o` ≈ 0 → компенсація 1 — пресет AC20 без змін. **Shakan** (σ 0.5, λ 25°): нахил λ виключено з `o`; max |θ| ≈ 25 + 0.5·47·1.3 + 3 ≈ 58° < 90°; хорда ≈ 25° ± 4° (λ ≤ 30°, рішення власника).

Еталонний алгоритм (C#-порт `simulateOneHour`):

```csharp
double hourlyBase = species.KBase / 24.0;
double hourlyTemp = 0.012 * Math.Max(0, T - 22.0) / 24.0;
double hourlySun  = isDay ? 0.05 * (1.0 - Clamp01(cloudCover / 100.0)) / 24.0 : 0.0;
double freeze     = T <= 0 ? Math.Max(0.05, 1.0 + T / 10.0) : 1.0;
double raw        = (hourlyBase + hourlyTemp + hourlySun) * (hasMoss ? 0.7 : 1.0) * freeze;
const double eMax = 0.30 / 24.0;
double evaporation = eMax * Math.Tanh(raw / eMax);
double rain = (precip > 0 && T > 0) ? 1.0 - Math.Exp(-Math.Clamp(precip, 0, 100) * 0.12) : 0.0;
moisture = Clamp01(moisture + rain - evaporation);
```
